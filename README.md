# Проекти:
DdexInvoicing - модуль DDEX
DdexInvoicingLib – бібліотека для роботи DDEX
Fixation - модуль «Фіксації порушень», WinForms, відокремлений
IpsCommonTypes – бібліотека (класів) спільних типів для клієнтської та серверної частини (обмін даними)
IPSComponentLibrary – бібліотека спільних WinForms контролів, відокремлених з проекта IpsViewComponentLibrary для уникнення зациклення ссилок між проектами
ipsFormsDesign – бібліотека класів (відповідна Model EF Core з WebAPI, але для клієнтської частини комплекса), деяких утиліт, сервісів для обміну даними з сервером
ipsFormsDesign.Tests – UnitTest проект, тести застарілі, часткові
ipsmedserviceapp – ASP.NET Core WebAPI комплекса, Model EF Core (відповідає певному переліку таблиць БД, деякі табличні ф-ї та в’юшки), контроллери, утиліти
IPSModulesLibrary – бібліотеки WPF контролів (складні контроли, модулі)
IPSModulesLibrary.Test – проект для тестування WPF контролів/модулів
IpsViewComponentLibrary – бібліотека WinForms контролів/форм комплеска
IPSViewComponentLibraryWPF – бібліотека WPF контролів/вікон компекса
LanguageLibrary – бібліотека для роботи функціоналу мовних локалізацій (багатомовності); працює з XML; має класи локалізації, для використання в контролах необхідно додати клас локалізації в контролі та бібліотеці (якщо таких нема), оновити та заповнити XML документ в модулі LanguageService на необхідній мові, скористатись відповідними методами отримання/присвоєння отриманих з XML даних в екземплярах відповідного класа; потребує завершення, документації, можливо зміни місця збереження даних з XML файлів на БД
LanguageService – модуль  роботи (зміна значень мови) з мовними локалізаціями комплекса; може працювати окремо
Launcher – стартова точка комплекса (клієнт), запуск всіх модулів здійснюється після авторизації
MediaServiceDb – проект БД комплекса
PartnersWorkplace – модуль «представники ОКУ»
RepNew – модуль «звітності», WinForms, відокремлений
ReportsLibrary – бібліотека звітів для модуля «звітності»
RoyaltyServiceInstaller – проект для створення інсталятора комплекса (розширення)
Settings – потенційний WinForms проект налаштувань комплекса (концепція, початий/незавершений), налаштування підключення до всіх WebAPI/БД, «прозвонка» для визначення чи правильно налаштовано IIS, WebAPI, логіни БД, різні права де це необхідно і т.д. після розгортання/оновлення комплекса
SmRoAccessAdmin – модуль «управління правами та доступами користувачів комплекса», WinForms, відокремлений
SmRoPermitApi – ASP.NET Core WebAPI модуля «управління правами та доступами користувачів комплекса», авторизація, CRUD користувачів, зміна повноважень користувачів
SmRoPermitClientLib – бібліотека класів для «управління правами та доступами користувачів комплекса» (клієнтська частина)
SmRoPermitCommonLib – бібліотека класів для модуля «управління правами та доступами користувачів комплекса»
SmRoPermitServerLib - бібліотека класів для модуля «управління правами та доступами користувачів комплекса» (серверна частина)
sysAdminwp – модуль «довідники системи», потребує доопрацювання, зміна langCode з формату aa на aa-AA, згідно загальноприйнятого, WinForms, відокремлений
WebAPIConnector – бібліотека класів, REST, використовується в сервісах бібліотеки ipsFormsDesign, обгортка для HTTP запитів для обміну даними з WebAPI 
WorkReport – модуль «роботи зі звітами та ідентифікація творів», WinForms, відокремлений

•	Відокремлені модулі – це фактично проект обгортка над контролом або групою контролів, деякі відокремлені модулі поглинув проект Launcher, в папці WorkplaceModules створюється Window який фактично така ж обгортка, але на WPF, контроли в ньому як WinForms так і WPF;
•	Вихідний тип модулів – Class Library (окрім Launcher, Settings, LanguageService);
•	Бібліотеки контролів IpsViewComponentLibrary та IpsViewComponentLibraryWPF - в першій WinForms контроли, в другій переведені на WPF першої;
•	В рішенні наявні залишки спроб паттерна схожого MVP, Model, View та Presenter в одному варіанті під кожну задачу тому його застосування себе не виправдало, можливо закладена  неправильна або складна реалізація, інший варіант - контроли використовують необхідні їм «сервіси» в code behind для обміну даними;
•	Тех. Документація практично відсутня, коментарі в деяких бібліотеках класів та модулях можуть бути частково або повністю відсутні, а в деяких наявні, частково наявна XML документація;
•	Наявні мертві контроли, мертвий код, рефакторинг майже не проводився, або проводився частково;

# Вміст рішення:
Утіліти – папка з утилітами;
webDeploy – папка з опублікованими в пакет WebAPI, які далі використовуються для розгортання;
publishModel.ps1 – PowerShell скрипт, після оновлення EF структури (класи, Model) БД через Scaffold в проекті ipsmedserviceapp потрібно запустити скрипт через Package Manager Console, він оновить структуру (класи, Model) в проекті ipsFormsDesign клієнтської частини комплексу, проставить атрибути [JsonIgnore] згідно файлу JsonIgnore.xml;
SetJsonIgnore.ps1 – PowerShell скрипт, використовується та запускається в попередньому, проставляє атрибут [JsonIgnore];
JsonIgnore.xml – XML документ з назвами EF класів та їх властивостей і т.д. (відповідають таблиці БД) в яких потрібно проставити атрибут [JsonIgnore] за винятком елементів noignore (може бути ссилка в таблиці на іншу таблицю, в якій в свою чергу є ссилка на попередню – зациклення, так EF будує структуру за стандартними налаштуваннями)
